# 5. Gap Analysis

Prioritized list of architectural improvements, ordered by what matters most for LLM-driven orchestration. **Ordering rationale:** LLM orchestration fails in a strict dependency order — (1) if tools can't be *discovered accurately*, planning fails outright → discoverability/capability metadata first; (2) if results can't be *traced*, chaining and reasoning over artifacts is impossible → provenance second; (3) if *identity/naming* is inconsistent, cross-repo composition breaks → consistency third; (4) then execution state, visualization, and docs hygiene, which improve quality but don't block the core loop.

---

## Tier 1 — Tool discoverability & capability metadata (LLMs can't plan reliably)

| # | Issue (evidence) | Sev | Impact | Recommended Solution | Complexity |
|---|---|---|---|---|---|
| 1 | **Stale tool inventories in docs**: gdm README says 20 tools (24 actual); erad 26 (27); shift 33 (36) | High | LLM planners grounding on docs/manifests get a wrong capability set → tool-call plans fail at runtime | Derive README/manifest from live MCP registration (single source of truth); CI check fails on drift | S (per repo, mechanical) |
| 2 | **Hardcoded `COMPONENT_MAP`** in gdm knowledge (`src/gdm/mcp/knowledge/documentation.py:35-50`, 14 of ~20 component classes) | High | LLM receives a false component inventory → invalid plans for component-targeted ops | Introspect the pydantic component registry at startup instead of a static map | S |
| 3 | **No capability metadata beyond tool names**: gdm/gdm-flow have no resources/prompts; `model_ref`/`system_path` semantics only in descriptions | High | LLM can't distinguish the four divergent "system summary" tools (gdm, erad, ditto, shift) or load context before planning | Add resources (registry/system catalog), rich per-tool descriptions, shared param-convention doc | M |
| 4 | **Duplicate MCP functionality with divergent names/schemas** (system summary/component query in 4 repos; model loading 4 ways) | High | Tool-routing ambiguity for orchestrators; cross-repo chaining requires normalization shims; planner wastes context on disambiguation | Ecosystem-wide tool-naming convention (`<domain>_<verb>_<noun>`, e.g. `gdm_get_system_summary`, `flow_run_ac_opf`); convention lint | M |

## Tier 2 — Metadata & provenance (results can't be trusted or chained)

| # | Issue (evidence) | Sev | Impact | Recommended Solution | Complexity |
|---|---|---|---|---|---|
| 5 | **gdm-flow `runs` table stores no model ref/hash/GDM version/config snapshot** (`sqlite_export.py:39-45`) — untraceable run IDs | **Critical** | Knowledge-graph edges `generated by`/`derived from` unbuildable; reproducibility impossible; agent memory poisoned with untraceable results | Standard artifact-manifest sidecar (JSON: model_ref, model_hash via `gdm.hashing_utils.hash_model`, tool+version, config snapshot, timestamps, `schema_version`, `derived_from`) written per run — mirrors the DistributionSystem JSON + `_time_series/` sidecar pattern | M |
| 6 | **Implicit model-registry contract, no service**: gdm/gdm-flow/erad resolve `model_ref` via SQLite `models(model_id, version, stored_path)` + `DIST_STACK_MODEL_REGISTRY_DB`; ditto/shift use plain paths/in-memory | **Critical** | Model identity across repos is an unowned convention — LLM can't reliably hand a model between tools by reference; ditto/shift are off-contract | Define and ship the registry contract (schema, env resolution, lookup semantics) as a small shared library or the sibling service; migrate ditto/shift onto it | M–L |
| 7 | **Plugin entry-point mismatch**: erad_plugins declares `erad.plugins` entry points (4× pyproject.toml:40-43); ERAD core has no discovery — one hardcoded optional import (`mcp/simulation.py:313`) | **Critical** | The plugin architecture is fictional: adding a plugin requires core edits; LLM capability surface can't grow dynamically; 3 of 4 plugins unreachable via ERAD | `importlib.metadata` entry-point discovery in ERAD core; shared plugin SDK (Config/Result/simulator/converter/scenario base contracts) to end quadruplicated `_require_engine` guards | M |
| 8 | **erad sim metadata lacks ERAD version/curve-set hash/input-model hash**; plugin results in-memory only (`artifacts/` empty) | High | Resilience results can't be re-derived, chained, or audited | Stamp run metadata (version, `DEFAULT_FRAGILTY_CURVES` hash, input hash); persist HazardSystem → GDM JSON + TS folder + manifest on completion | M |
| 9 | **No schema version in exported artifacts** (gdm-flow sqlite_export, erad parquet/JSON, etc.) | Medium | Future readers can't migrate; knowledge-graph ingestion ambiguous; `data_format_version` pattern exists in gdm but isn't propagated downstream | Stamp `schema_version` in every exporter (mirror gdm's init-time stamping) | S |
| 10 | **CIM round-trip lossy**: ditto writer synthesizes `uuid5` mRIDs (`cim_iec_61968_13/write.py:52-53`); original mRIDs lost | Medium | Identity breaks at the format boundary of the many→one→many chain; cross-repo node linking fails for converted models | Preserve mRIDs in GDM extension fields or a sidecar identity map | M |

## Tier 3 — Naming consistency, serialization, execution state

| # | Issue (evidence) | Sev | Impact | Recommended Solution | Complexity |
|---|---|---|---|---|---|
| 11 | **run_id prefix vs implementation key mismatch** (`ac/pf/dc/lindistflow` vs `ac_opf/ac_pf/dc_opf/lindistflow`, `sqlite_export.py:26-27,1031-1064`); `violation_kind` mixes `"overvoltage"/"over"` (`sqlite_export.py:337,553`) | Medium | Artifact refs and future KG edges built from run metadata will mismatch; LLM cross-references run IDs to solver names incorrectly | Single source-of-truth enums exposed via MCP; alias map for backward compat | S |
| 12 | **MCP sub-version decoupling**: gdm mcp 0.1.0 vs package 2.3.7; erad mcp 1.0.0 vs 0.1.14; shift ServerConfig 0.1.0 vs 0.8.0; plugin register() 0.1.0 vs 0.1.2 | Medium | Version/capability negotiation impossible; agent memory of "tool version" untrustworthy | Single `__version__` source; MCP server info advertises package + protocol versions; plugin version from package metadata | S |
| 13 | **Dependency pin inconsistency**: gdm-flow `>=2.3.7` vs erad/ditto/shift `==2.3.7` | Medium | Upgrade deadlock: a 2.3.8 patch or 2.4.0 either stalls or breaks pinned repos | `~=2.3.7` compatible-release pins + cross-repo CI test matrix | S |
| 14 | **Execution state inconsistent**: stateless gdm-flow; in-memory ephemeral ServerState (erad, 8-char IDs); `_SYNC_STATE` module singleton (ditto, docstring claims unimplemented lifespan); per-session AppContext (shift) | Medium | Multi-agent workflows can't resume or share sessions; session loss = result loss | Define a shared run-state + artifact-store contract (SQLite, run_id-keyed — extend gdm-flow's schema); make state explicit per repo | M–L |

> **Resolution (Gap #14, doc 11 §1):** the shared run-state contract is now **`dist_stack.runstore`** — a new SQLite run-state + artifact store in dist-stack, keyed by `run_id`, adopted best-effort/write-only by all five domain repos.

## Tier 4 — Visualization, validation, workflows, hygiene

| # | Issue (evidence) | Sev | Impact | Recommended Solution | Complexity |
|---|---|---|---|---|---|
| 15 | **No plotting/GIS MCP anywhere**: `to_gdf`/`to_geojson`/`plot` Python-only in gdm (distribution_system.py:636-810); dashboards in gdm-flow; plots in erad | Medium | Human-in-the-loop review and report generation dead-end; agents can produce runs but not deliver visual artifacts | Add `plot_system`/`to_geojson` (gdm), `plot_ts`/`dashboard` (gdm-flow), plot/export tools (erad); standard artifact output paths | M |
| 16 | **MCP diagnostics re-implement validation** (phase consistency, matrix dims, array lengths; `mcp/validation/diagnostics.py:50-54`) instead of `System.validate()`; `hashing_utils` unused by MCP | Medium | Dual implementations drift; `apply_fixes` may diverge from core; LLM sees inconsistent validation semantics across tools | MCP tools delegate to core validation/hashing; keep re-implementations only as message formatting | S |
| 17 | **Prompts only in ditto/shift**; no canonical workflow templates in gdm/gdm-flow/erad | Medium | LLM planners reinvent multi-step recipes (validate→reduce→opf→export→plot) every session; no reusable workflow components | Add versioned MCP prompts per repo encoding canonical workflows | S–M |
| 18 | **No cross-tool artifact linking** (nothing says "plot X visualizes run Y", "export Z derives from model M") | High (for KG future) | The knowledge graph can't be built retroactively; artifact reasoning impossible | Manifest `derived_from`/`references` fields; convention for artifact directories | M |
| 19 | **Missing MCP ops that complete the workflow loop** (gdm: tracked_changes apply, kron/geometry, split-phase, TS reads, catalog/dataset/cost; gdm-flow: AC-PF/QSTS/multiperiod; erad: engine SQL/parquet/csv/arrow, elevation, EditStore, scenario application; ditto: CYME; erad_plugins: everything) | High | Orchestration dead-ends: a workflow can reduce/run/export but not visualize, apply a scenario back, or read TS values → agents fall back to Python, breaking MCP-native execution | Staged tool additions per repo, ordered by workflow value (TS reads + scenario application + plotting first) | L aggregate (each tool S–M) |
| 20 | **Docs/CLI hygiene**: dead gdm CLI params (`--host/--port/--allow-auto-fix`, server.py:1061); phantom `[sparse]/[optimization]` extras (README vs pyproject); ditto ARCHITECTURE.md/API.md cite non-existent modules; shift `_DOC_FILES` missing CHANGELOG/IMPROVEMENTS (server.py:22,24); erad `DEFAULT_FRAGILTY_CURVES` typo; doc-tooling repo-relative paths (gdm `find_gdm_repo`, gdm-flow docs/ breaks in wheels) | Low | Trust erosion; LLM docs-grounded planning hits dead ends; docs search fragile in deployed envs | Doc/CLI lint CI; package docs via `importlib.resources`; centralize doc tooling | S |

**Priority order:** Tier 1 (#1–4) blocks planning → Tier 2 (#5–8) blocks reasoning/chaining → Tier 3 (#11–14) blocks composition → Tier 4 (#15–20) blocks polish. #19 (MCP coverage) is high-impact but its *first tranche* should land with Tier 2, because workflow-completion tools are worthless without provenance to chain them.
